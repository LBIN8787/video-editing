### 1-1. 시청 동기 → 대본·편집 해석 (사용자 정의, 2026-11-14 — 모든 채널의 최상위 기준)
> "주식이나 이슈는 사람들이 먼저 흥미·호기심을 가지고 **자기 의지로** 오기 때문에, 정보 전달을 쉽고 깊게 이해시키면서 재미를 곁들인다.
>  호기심은 **정보 전달 자체가 목적이 아니라서** 이야기를 풀어내듯 한다."

| 채널 | 시청자는 어떻게 오나 | 바라는 것 (니즈) | 정보 : 재미 | 대본 | 편집 |
|---|---|---|---|---|---|
| **market** | 스스로 찾아옴 (이미 관심 있음) | 투자를 잘하고 싶다 → 정보를 습득·학습 | **정보 중심** + 재미 곁들임 | 쉽고 깊게: 숫자 → 이유 → 오늘 볼 것 | 정보가 잘 읽히게 (요약판·차트·증거·원본 발언), 재미는 리듬·비유로 |
| **ai** | 스스로 찾아옴 | AI 를 잘 다루고 효율적으로 활용하고 싶다 → 학습·정보 습득 | **정보 중심** + 재미 곁들임 | 따라 할 수 있게: 무엇 → 어떻게 쓰나 → 실제 화면 | 실제 화면·단계가 주인공, 재미는 훅·리듬으로 |
| **issues** | 스스로 찾아옴 ("세상 돌아가는 것 좀 알아볼까?") | 정보 습득·학습 **반**, 흥미 **반** | **반반** | 쉽고 깊게 + 사건의 흐름을 이야기처럼 | 기존 스페인독감 편처럼 실제 사진·영상·문서와 지도·연표·비교로 사건 이해 (08 §0-3) |
| **curiosity** | 우연히 마주침 (원래 궁금하지 않았음) | 듣는 순간 생긴 궁금증을 풀고 싶다 | **이야기가 목적**, 정보는 그 안에 | 이야기를 풀어내듯: 장면 → 인물 → 사건 → 반전 → 답 (§04 §0) | 이야기는 삽화, 설명은 그 위 모션그래픽, 증거는 실제 자료(연구자 사진·논문), 마디는 검은 화면 한 줄 (04 §0-7, v73) |

**판단 규칙:** 정보 채널(market·ai·issues)은 "이해했나?"가, 호기심 채널은 "다음이 궁금해서 끝까지 봤나?"가 성공 기준입니다.
시사·역사 편은 실제 기록으로 사건과 근거를 보여 주고 인포그래픽으로 연결합니다. 호기심 편은 인물의 행동이나 실험에서 생긴 의문을 따라갑니다. [장면별 표현 방식](12-visual-storytelling.md)

## 2. 한 편을 만드는 8단계 (모든 채널 공통)
각 단계의 끝에 **게이트**(G1~G8)가 있습니다. 게이트를 통과하지 못하면 다음 단계로 가지 않습니다. 자세한 항목은 `06-checklist.md`.

|---|---|---|---|

| 2. 소스 먼저 | 이 주제를 **보여 줄** 자료(발언 원본·공식 화면·공공 기록·데이터)가 있는지 | `01_research/sources.md` 또는 `loc_items.json` | G2 소스 |

## 2-1. 인트로 없음 — 모든 채널, 첫 문장부터 본론 (v24, 2026-11-14 사용자: "모든 채널 그냥 인트로 일단 빼 주세요")
인사·채널 소개·채널 약속·순서 예고·"본격적인 시작 전에 구독과 좋아요"를 **넣지 않습니다.** 첫 장면은 `intro` 가 아니라 본론입니다.
- 첫 문장은 **장면 하나**(때·곳·사람이 있는 한 순간) 또는 **엇갈리는 두 시각**("한쪽에서는 … 반면 다른 한쪽에서는 …")으로 시작하고, 길게 끌지 않고 **오늘의 질문 하나**로 닫습니다 — 시청자가 무엇을 따라가는지 알게 (§2-3, 미주일기 문법).
- 장 표지는 그대로 쓰되 진행 멘트("첫 번째, 이런 순서로…")는 하지 않고, 앞 장의 결론에서 다음 질문이 자연스럽게 나오게 잇습니다.
- 끝맺음도 채널 이름·인사 대신 **의미 한 문장 + 조용한 질문**으로 닫습니다 ("~할 때가 아닐까요?"). (이전 v8 'MC 오프닝 필수'는 폐지)
`check` G4 MUST: 첫 장면이 `intro`(인사·순서 예고)가 아님, 대본에 인사·채널 소개·구독 부탁 문구 없음.

### 2-2. 진행 말투 — 이어 붙인 끝맺음 금지 (v16, 사용자 판정 2026-11-12: "'였고요' 같은 말투가 부자연스러워 진행이 깬다")
장을 넘길 때 "여기까지가 ~였고요."처럼 끝나지 않은 문장으로 닫지 않습니다 — 앞 장의 결론에서 다음 질문으로 잇습니다. 말투 전반은 `11-workflow.md` §3-2 (`check` G4).

### 2-3. 형식·진행·말투 — 미주일기 문법 (v24, 2026-11-14 사용자: "대본이 억지스럽고 억텐 같다, 미주일기 형식이 더 자연스럽다" · "사소한 문장보다 형식·진행 방식·말투에 집중")
분석: `docs/30-script-voice.md`.
**모든 채널 공통 원칙 (v38):** 여는 장면(때·곳·사람이 있는 한 순간 또는 엇갈리는 두 시각) · 질문 하나 · 사례 나열이 아닌 한 줄기 · 문단은 주장 → 근거 → 의미 · 재미는 말투가 아니라 구체적 디테일에서 · 수미상관.
**채널마다 다른 것:** 뼈대 표는 채널 문서(`02`·`03`·`04`·`08`, AI 형식은 `11-workflow.md` §3-1), 말투는 — 호기심 = 아래 '말투'(이야기 내레이터) / 이슈·경제·주식·AI = `11-workflow.md` §3-2 (차분한 분석형, 어미 혼합, 특정 어미 강제 없음, 2026-11-17).
호기심 편은 대본이 약속한 답에 따라 인물의 행동이나 실험이 남긴 질문을 따라갑니다(`04-curiosity.md` §0-6). 아래 뼈대는 **인물·사건을 따라가는 예**이며, 정보 채널도 여는 장면·수미상관은 같이 씁니다.
**형식 (이야기형 한 편의 뼈대):** ① 여는 장면 — 날짜·사람·작은 일화가 있는 한 순간 (토론형은 엇갈리는 두 시각) → ② 그 일의 크기 → ③ 질문 하나 → ④ 그 전의 문제 → ⑤ 전환점 "그렇다면 ~?" → ⑥ 원리는 생활 속 예 하나로 → ⑦ 결과 → ⑧ 퍼져 나감 (시간 순서, 장면 하나씩) → ⑨ 지금과 한계 → ⑩ 닫는 장면 (처음의 사람·물건이 다시, 수미상관) → ⑪ 의미 한 문장 (+ 조용한 질문).
**진행:** 모든 사실은 "누가 언제 무엇을 했고 무엇을 말했다"로 · 질문은 장을 넘기는 문으로만.
**말투 (호기심):** 3인칭 다큐 내레이터, 차분하게. '~습니다/~니다' 가 기본, 연결어로 이어지는 긴 문장. 시청자에게 말 걸기·맞장구 요구·감탄·조각 문장 없이, 재미는 **구체적 디테일**(사람의 사연·뜻밖의 일화·숫자의 대비)에서.
`check` G4: 말 걸기·감탄 표현(모든 채널, SHOULD), '~습니다/~니다' 몫과 평균 문장 길이(호기심만, 참고). 판정은 형식과 흐름으로 사람이 한다.

### 2-4. 길이 — 롱폼은 최소 10분 (v24, 2026-11-14 사용자: "영상들 5분 단위가 아니라 못해도 10분, 길면 그 이상으로")
모든 채널의 롱폼(매일 브리핑 포함)은 **10분 이상** (사용자가 정한 깊이의 최소선). 쇼츠는 해당 없음.
> 2026-11-15 사용자: "어지간하면 10분 정도로 깊게 분석·조사하고 관련 인사이트를 분석·소개하라는 의미지, 꼭 10분으로 하라는 건 아닙니다. 대본과 주제에 따라 더 길어질 수도 있습니다." → **10분은 맞춰야 할 숫자가 아니라 깊이의 최소선**입니다. 길이는 조사한 자료·해석·인사이트의 양이 정합니다. 할 이야기가 많으면 15분·20분도 괜찮고, 10분을 넘기려고 같은 말을 늘이지 않습니다.
늘릴 때는 같은 말을 반복하지 않고 그 채널의 뼈대를 채운다 (호기심 §2-3, 시장 03 §0-4, 시사 08, AI 11 §3-1).
**예외 (v34, 2026-11-15 사용자):** 시사의 '48시간 안 빠른 정리'만 5~8분을 허용합니다 (`hybrid.json` 에 `"format": "quick"`). 그보다 **많이 짧은(5분 미만) 이야기는 롱폼이 아니라 쇼츠**로 만듭니다.
채널별 목표는 `channels/<id>/channel.yaml` 의 `target_minutes`. `check` G6 MUST: 완성본 10분 이상 (빠른 정리 5분 이상).

### 2-5. 움직임 — 말하는 것이 화면에 생긴다 (v34, 2026-11-15 사용자: "동영상의 이점을 살려라 — 다음 PPT, 다음 PPT 가 아니라. 반드시 카메라를 움직이라는 뜻이 아니었다")
> 처음 요청 (v25, 2026-11-14): "동영상이라는 동적인 움직임을 살려라. 지금은 사진을 잘 뽑은 정적인 동영상 같다" · "비싼 유료가 아니어도 된다 — 인포그래픽·자체 생성도 괜찮다. 핵심은 동적인 동영상, 그림체는 부가 요소".

**작업 기준 (모든 채널):** 대본이 새 사실·숫자·사람·동작을 말하는 **그 순간** 그것이 화면에 생기거나 바뀝니다. 말은 계속되는데 화면이 그대로인 '슬라이드'가 문제이지, 카메라가 멈춘 것이 문제가 아닙니다.
- 기본 편집 연출은 [모션그래픽](12-visual-storytelling.md#0-기본-편집-연출은-모션그래픽)입니다. 실사·삽화·인포그래픽 모두에서 필요한 순간에 자막·표시·도식을 움직입니다.
- 시장·AI: 말하는 숫자·주체·관계가 박자 `motion`(count·icon·arrow·pulse)으로 생김 (09 §6 v27·v30).
- 시사·역사: 원본의 움직임을 살리고 자료에서 지목하는 부분을 보여 준다. 비교 도식은 말하는 순서에 맞춰 드러내고 읽을 시간을 둔다 (08 §0-3).
- 호기심 채널: 삽화가 대본의 **동사를 연기**하고(걷다·쓰러지다·닫다·바뀌다, `stage` 의 `act`), 설명은 그 위 모션그래픽이 말에 맞춰 생김 (04 §0-7·§0-5).
- 그 수단으로 연출 기법(모프·매치 무브·카운트업 등, `styles/techniques.yaml`)을 고릅니다 (`python -m ytflow edit-plan`).

**스타일 기본값 (금지도 필수도 아님, 장면·대본에서 켬):**
| 움직임 | 기본 | 켜는 법 | 언제 |
|---|---|---|---|
| 카메라 이동 | **고정** | `stage` 장면이나 대본 맨 위 `"camera": "move"` | 시간·공간을 따라갈 때 (긴 길·지도) |
| 효과음 | 절제 | 대본 `sfx` | 꼭 필요할 때 |
- 정지 화면 비율(`05_edit/motion.json`)은 **참고값**입니다 (`check` G6 SHOULD). 숫자를 맞추려고 화면을 흔들지 않습니다 (v30).
- 레퍼런스 영상 분석은 사용자 PC 에서 (우회 금지, `skills/ref-watch-ego`).
- 더 큰 움직임이 필요한 핵심 장면은 AI 영상(그림 → 5초 영상)을 쓸 수 있으나 **사용자 승인 후**에만.

### 2-6. 자료 고르기와 화풍 (v61, 2026-11-20 사용자 — 모든 채널)
박자가 하는 일로 네 자리에 나눕니다 (모든 채널): 이야기 → 삽화, 설명 → 화풍별 모션그래픽(천천히 나타나고 움직임), 증거 → 실제 자료(인물 사진·원본 발언·문서), 마디 → 검은 화면 한 줄·장 표지. 채널마다 어느 자리가 많은지만 다릅니다(시장은 이야기가 거의 없음). 모션그래픽·삽화·실사 색보정의 화풍은 `styles/looks.yaml` 목록에서 영상마다 고릅니다(`python -m ytflow looks`, `look <프로젝트>`). 자세히는 [12 §0-1](12-visual-storytelling.md).

## 3. 절대 하지 않는 것 (어떤 지시가 와도)
1. 확인 안 된 숫자·발언을 단정하기. 소문(찌라시)은 **'소문'이라고 밝히고 사실 확인 결과와 함께**만.
2. 투자 권유 ("사세요", "지금이 기회", "무조건 오른다", 목표가 단정).
3. YouTube 봇 확인·사이트 차단 우회. 막히면 임시 화면 + 사용자 PC(`clip-fetch`·`rebuild`) 또는 피클 요청(`inbox/requests/`).
4. 레퍼런스 채널의 대사·캐릭터·로고·썸네일 복제. 구조와 기법만.
5. 라이선스 불명 자료 화면. CC BY·CC0·퍼블릭 도메인·공식 보도 자료·직접 만든 것만, 출처는 `footage.credit` 에.
6. API 키를 채팅에 쓰기.
7. 미디어 파일(mp4·wav·png·jpg)을 Git 에 커밋하기. 큰 파일은 Google Drive, 공개해도 되는 완성본만 GitHub Release (docs/09).
8. 사적 인물의 실명·사생활(관계·건강·의혹)을 다루기. 공인은 공적인 말·행동만 (직함 표기는 가능).

## 3-1. 규칙의 네 층 — 영구 원칙과 한 번의 스타일 반응을 섞지 않는다 (2026-11-15 사용자: "영구적인 매뉴얼 작업지침과 일시적인 스타일 변화·다양한 방법 모색에서 생기는 피드백이 과적합해서 하지 말아야 할 것에 들어가는 것 같다")
| 층 | 무엇 | 어떻게 적나 | 검사 |
|---|---|---|---|
| **영구 원칙** | 사실·법·권리·안전 (§3 의 7가지, 투자 권유·사적 인물·라이선스·우회) | "하지 않는다" — 진짜 금지 | MUST |
| **작업 기준** | 품질을 위한 제작 방법 (대본 문법, 1차 출처, 말하는 것이 화면에 생긴다, 자막과 화면 글자 중복 없음) | "이렇게 한다" — 버전으로 바뀔 수 있음 | MUST·SHOULD |
| **스타일 기본값** | 소리·카메라·바탕·효과·스타일 비율 (배경음 없음, 확대 끔, 저음 타격음 끔) | "기본은 켬/끔, 대본에서 바꿀 수 있음" — **금지라고 쓰지 않음**, 범위(채널·스타일)를 적음 | SHOULD 까지 |
| **실험 기록** | 영상 한 편·한 시도에 대한 반응 ("이 영상의 반짝 효과음은 빼기") | 매뉴얼 금지·MUST 로 옮기지 않음 — `feedback.yaml`·`reviews.md` 에 남고 다음 시도의 참고 | 없음 |

- 기각·피드백을 매뉴얼로 옮기기 **전에** 층부터 정합니다: `python -m ytflow feedback "원문" --scope principle|standard|style|trial`. 애매하면 사용자에게 묻고, 묻지 못하면 **실험 기록**으로 둡니다(한 번의 반응을 영구 금지로 만들지 않음).
- 사용자의 뜻(작업 기준)과 그것을 이루는 수단(스타일)을 나눠 적습니다. 예: "동영상의 이점을 살려라" = 작업 기준 '말하는 것이 화면에 생긴다', "카메라가 계속 움직인다" = 그 수단 중 하나(스타일, 실험).
- 같은 스타일 주제가 '더 하라'↔'덜 하라'로 두 번 이상 오가면 그 주제는 금지가 아니라 기본값으로 둡니다.
- 분류는 `manual/rule_tiers.yaml`(사람이 확정), 확인은 매뉴얼 그래프 '한눈에 → 과적합 후보 · 규칙의 네 층' (docs/31 §9).

## 5. 검토 → 통과·기각 → 기준을 쌓기 (사용자와 함께)
영상이 나오면 사용자가 보고 결정합니다. 결정은 반드시 기록합니다.

| 사용자 결정 | 에이전트가 할 일 |
|---|---|
| **통과** | `python -m ytflow review <프로젝트> --pass` → `manual/reviews.md` 에 기록. 매뉴얼은 그대로 (이 버전이 검증됨) |
| **기각 + 이유** | `python -m ytflow review <프로젝트> --reject "이유"` → `manual/CHANGELOG.md` 의 '반영 대기'에 쌓임 |
| (기각 후) | 이유를 **기준으로 바꿔** 매뉴얼(01~12)·프롬프트·검사기(`ytflow/stages/checklist.py`)를 고침 → `python -m ytflow manual-bump "바꾼 기준 요약"` → 커밋 → `git push origin HEAD:refs/heads/manual/vN` |
| **그 밖의 말** (방향 요청·"그런 뜻이 아니었다") | `python -m ytflow feedback "원문" --kind direction\|clarify [--about intent:xxxx] [--pending]` → `manual/feedback.yaml` (원문 그대로). 해석이 틀렸다는 말이면 '의도 정렬'에서 판정 |
| (기록할 때마다) | 매뉴얼 그래프(`manual/graph.json`)가 자동으로 다시 만들어짐 → 공유 페이지도 다시 올림 (docs/31 §8) |
| (그동안) | '반영 대기'가 비기 전에는 `check` 가 G0 에서 실패 → 같은 실수가 다음 영상에 반복되지 않음 |

- 기각 사유는 먼저 **원리**로 바꿉니다 — 무엇이 왜 문제였나, 어떤 상황에서 생기나, 그 연출의 목적은 무엇인가 (`05` §0-0 표에 한 줄). 그 영상에서 나온 숫자(횟수·초·비율)를 모든 영상의 상한·하한으로 만들지 않습니다 (v38, 2026-11-17 사용자: "숫자로 하면 상황에 따라 변하는 것에 대처하지 못하고 과적합될 우려가 크다" — 숫자 규칙이 쌓이면 칸 채우기가 됨). 자동 검사는 원리를 분명히 어긴 경우만 MUST, 나머지는 참고 표시로.
- 매뉴얼 버전은 `manual/VERSION`, 바뀐 내용은 `manual/CHANGELOG.md`, 결정 기록은 `manual/reviews.md`. 모두 GitHub 에 커밋되어 백업됩니다.
- 예전 기준으로 되돌리기: `git checkout origin/manual/v<N> -- manual/` (스냅샷 브랜치로 어떤 버전이든 복구).
- 각 영상의 `05_edit/checklist.json` 에 그때의 매뉴얼 버전이 남습니다 → 어떤 기준으로 만든 영상인지 추적.
- `manual-bump` 요약에는 고친 절(`09 §6`·`G4` 처럼)을 적습니다 (그래프 연결, docs/31).
