# 11. 제작 업무 체계 — 한 편을 처음부터 끝까지 (매뉴얼 v38, 2026-11-17 확정)

> 상태: **확정 (2026-11-17 사용자 승인, 매뉴얼 v38).** 모든 롱폼 제작의 작업 순서표입니다. 무엇을 쓰나(장면·연출)는 `10-when-to-use.md`, 이 문서는 **누가·언제·무엇으로 통과를 판단하나**.
> 목적: 규칙을 더 쌓지 않고 **누가·언제·무엇을 만들고·무엇으로 통과를 판단하는지** 고정해서, 그럴듯하지만 속이 빈 영상(slop)이 나오는 구멍을 막습니다.
> **최종 승인은 사용자만 합니다.** 에이전트는 통과를 스스로 기록하거나 업로드·공개하지 않습니다.
> **예외 — 매일 시장 채널(`ch-market-daily`, 이어 읽는 시장):** 2026-11-17 사용자 결정 "자동으로 예약 공개로 해줘" — 브리핑·추가 편 모두 검사 통과 뒤 자동 예약 공개, 사용자 검토는 공개 뒤 (`09-market-daily.md` §2-1). 통과 기록(`review --pass`)은 여전히 사용자만.

v1 → v2 에서 바뀐 것 (2026-11-17 사용자 지시)
- AI 롱폼 형식을 하나로 고정하지 않음 → 주제마다 네 형식 중 고름 (§3-1)
- 뉴스레터를 주제 탐색의 첫 입력으로 (`inbox/newsletters/<날짜>.md` 자동 수집, `config/newsletters.yaml`·`docs/36`, S1)
- 이슈·경제·주식 내레이션: 차분하고 자연스러운 분석형, 어미를 강제하지 않음 (§3-2)
- 세 편을 같은 단계끼리 묶지 않고 **한 편씩 따로** 진행 (§2-1)
- 결정 지점마다 '보여 주는 것·묻는 것·기각되면 돌아갈 곳'을 정함 (§2-2)

### 2-1. 한 편씩 따로 진행 (v2)
- 세 편은 **각자의 S0~S9** 를 따로 갑니다. 다른 편의 결정을 기다리느라 멈추지 않습니다.
- 한 편이 결정 지점(★)에서 사용자를 기다리는 동안, 에이전트는 다른 편의 다음 단계를 진행합니다.
  ```
  AI     S0─S1 ★D1 ·········· S2─S4 ★D2 ······ S5─S6 ★D3 ··· S7─S8 ★D4 S9
  시사          S0─S1 ★D1 ···· S2─S4 ★D2 ······ S5─S6 ★D3 ··· S7─S8 ★D4 S9
  호기심               S0─S1 ★D1 ··· S2─S4 ★D2 ······ ...
  ```
- 결정 요청이 우연히 겹치면 한 메시지에 함께 보내되, 편마다 따로 답할 수 있게 나눕니다.

### 2-2. 결정 지점 — 보여 주는 것 · 묻는 것 · 기각되면 돌아갈 곳
| | 사용자에게 보여 주는 것 | 묻는 것 | 볼 시간 | 기각되면 |
|---|---|---|---|---|
| **D1 주제·형식** | `topic_card.md`: 후보 3개, 각각 질문 한 줄·`known` vs `new_angle`·점수·형식(ai)·핵심 자료 2개·뉴스레터 신호 | 어느 후보로? (다른 주제 지시 가능) | 3분 | S1b (이유를 카드 기준에 반영) |
| **D2 대본** | `script_v1.md` 전문 + 맨 위에 의도 한 줄·장 목록·예상 길이 | 이야기 흐름·깊이·말투 OK? | 10분 | S4 (구조 문제면 S3) |
| **D3 화면** | 샘플 영상 30~60초 + 장면표 요약(장면 type 분포) | 화면 방향 OK? | 3분 | S5 |
| **D4 최종 승인** | `final.mp4` + 제목 3 + 썸네일 A/B/C + `check` 결과 + 남은 일 | 통과 / 기각 + 이유 | 영상 길이 | 이유에 따라 S4·S5·S7 · 기각 사유는 `review --reject` → 매뉴얼 '반영 대기' |

- D1·D2 는 건너뛰지 않습니다. D3 는 사용자가 "샘플 없이 가자"고 하면 생략할 수 있습니다.
- 기각 뒤 사용자가 구판을 지정하면 그 릴리스의 매뉴얼·회차 설정·렌더러를 확인해 화면 방향을 다시 잡습니다. 다른 채널을 지정하면 실제 영상에서 확인한 컷과 화면 안 움직임을 회차 장면표에 연결해 D3 샘플로 확인합니다.
- 결정 요청에는 항상 **에이전트 추천 하나와 그 이유**를 붙입니다.

### 2-3. 작업 기록 — 수정하면서 작업하기
프로젝트 `REPORT.md` 에 단계마다 세 줄:
- **한 일**: 산출물 이름
- **혼자 판단한 것**: 매뉴얼에 기준이 없어 고른 것과 이유
- **막힌 것**: 접근 불가 자료·도구 오류·오래 걸린 곳

S9 에서 '혼자 판단한 것'을 §5 개정 기록에 옮기고, 사용자 OK 후에만 매뉴얼에 넣고 `manual-bump`.
작업 중 이 문서 자체가 실제와 맞지 않으면 그 자리에서 §5 에 적고 다음 결정 지점에 함께 묻습니다.

### 2-4. S3 첫 칸 — 목적 분간과 매체 질문 (2026-11-18 사용자, 근거 `docs/37`)
> "목적성 자체가 정보제공 목적이 큰지 아니면 취미나 유흥 즐길거리 목적인지 분간해야 해요. 그에 따라 연출이 달라지는 거구요" · "글과 PPT와 PDF 그리고 동영상의 특징과 차이점, 그리고 정보습득형·즐길거리형 등 시청자의 니즈를 생각해서 작업"

- **왜:** 같은 연출도 목적에 따라 득이 되기도 독이 되기도 한다. 정보 습득형에 이야기 연기를 길게 넣으면 핵심이 늦게 나오고, 즐길거리형에 요약판·숫자 쪽지를 넣으면 '설명 영상'이 되어 이탈한다.
- **어떻게 (S3, `02_script/intent.md` 맨 위):**
  ```
  목적: 정보 습득형 | 즐길거리형      (채널 기본: 시장·AI = 정보 습득형, 시사 = 반반이면 정보 습득형 쪽, 호기심 = 즐길거리형 — README §1-1)
  1) 시청자는 스스로 찾아왔나, 우연히 마주쳤나?
  2) 끝나고 남아야 할 것은 구조(이해)인가, 감정(여운)인가?
  3) 움직임을 이해에 쓸까, 몰입에 쓸까?
  ```
  세 답이 채널 기본과 다르면(예: 호기심인데 '구조'가 남아야 하는 편) 그 편만 바꾸고 이유를 한 줄 적는다.
- **연출 수단을 고르는 기준** (`docs/37` §2):
  - **정보 습득형** — 성공 기준 "이해했나": 말하는 숫자가 그 순간 생김·원인 → 결과 화살표·같은 축 비교·원문 형광펜, 근거(숫자·이름·출처)는 화면에 보임.
  - **즐길거리형** — 성공 기준 "다음이 궁금해 끝까지 봤나": 인물이 대본의 동사를 연기, 움직이는 소품으로 은유, 숫자 쪽지·정보 카드는 기억할 한 가지만.
- **매체 질문** (S5 장면 기획, `05` §0-0): 장면마다 "PPT 한 장이나 글 한 문단으로 바꿔도 똑같이 전달되는가?" — 그렇다면 무엇이 생기고·움직이고·바뀌어야 하는지 다시 본다.
- **검사:** `check` G4 SHOULD — `intent.md` 에 `목적:` 줄이 있는지만 본다 (어느 쪽을 골랐는지는 D2 에서 사람이 판단). 숫자 기준은 두지 않는다.

### 3-1. AI 롱폼 — 형식을 주제가 고른다 (2026-11-17 사용자)
형식을 하나로 고정하지 않습니다. S1b 에서 주제마다 아래 넷 중 **시청자가 얻을 가치가 가장 큰 형식**을 제안하고 D1 에서 함께 결정합니다.

| 형식 | 고르는 때 | 시청자가 얻는 것 | 대본 뼈대 | 화면 뼈대 | 필수 자료 |
|---|---|---|---|---|---|
| **주간 산업 뉴스** | 한 주에 큰 사건이 여럿, 서로 이어짐 | 업계가 어디로 가는지 | 사건을 나열하지 않고 **인과로 엮음**: 중심 사건 → 그것이 부른/연결된 사건 → 이용자에게 미치는 영향 → 볼 신호 | 뉴스 데스크 카드 + 인과 지도 + 공식 발표 캡처 | 1차 출처(회사 발표·공시·통신사) 2개+ |
| **도구 심층 분석** | 새 도구·기능이 나와 '써 볼 만한가'가 질문 | 쓸지 말지, 어떻게 쓸지 | 무엇 → **직접 써 본 결과** → 기능 검증(회사 주장 vs 실제) → 활용 방법 → 장단점·가격·한계 | 실제 사용 화면(녹화·캡처) + 단계 표시 + 비교표 | 직접 실행 화면, 가격·제한 |
| **실제 활용 사례** | 사람·회사가 AI 로 일을 바꾼 사례가 확인됨 | 내 일에 옮길 아이디어 | 사례의 장면(누가·무엇을) → 전/후 → 어떻게 했나 → 옮기려면 → 주의 | 사례 자료 화면 + 전/후 비교 + 흐름도 | 당사자 공개 자료(블로그·발표·인터뷰) |
| **기술·산업 트렌드 분석** | 여러 달에 걸친 흐름(칩·비용·규제·인력)이 한 지점에 모임 | 큰 흐름과 내 위치 | 지금의 신호 → 과거부터의 흐름(시간순) → 구조(누가 얻고 잃나) → 갈리는 해석 → 시나리오 | 타임라인·데이터 차트·인과 지도 | 데이터 출처 + 전문가 분석(이름·소속) |

## 7. 연출 인계와 화면 검토

S5에서 [장면의 표현 방식](12-visual-storytelling.md)을 고른다. 행동이 중심인 컷은 시작 상태·주체·변화가 일어나는 발화·끝 상태를 적는다. 자료가 중심인 컷은 확인할 근거·출처·보여 줄 부분·읽는 시간을 장면표에 남긴다. 화풍·원화 승인과 동작이 담긴 영상 승인을 각각 기록한다. 같은 대본을 다른 에이전트가 이어받으면 기존 장면표를 먼저 재생한다. 연출을 바꾸려면 새 판본으로 제시한다.

글자를 가린 상태에서도 책장이 들린 손이 멈췄는지, 주문을 받았는지, 부품이 어디에 끼워졌는지 읽을 수 있어야 한다. 클로즈업은 앞 구도에서 볼 수 없던 단서를 보여줄 때 선택한다. 손과 얼굴의 관계가 필요한 장면은 둘을 함께 담는다. 상자·연결선·라벨을 움직이는 형식이 사건을 대신하는 장면은 재편집한다. 통계의 단위·분모나 출처 원문은 읽을 수 있게 유지한다.

새 편은 대사의 원인과 다음 상태가 이어지는 대표 시퀀스를 소리와 함께 D3에 제시한다. 다음 에이전트가 읽을 곳은 프로젝트의 `02_script/EDIT_CONTEXT.md`, 장면표와 사용 판본이다. 고정 편집본의 기본 재생성 명령은 `python -m ytflow hybrid <프로젝트>`이다. [장면표 작성법과 제작 사례](../docs/42-script-to-motion.md)
