## 0. 왜 업무 체계가 필요한가

### 0-1. slop 이 생기는 자리
목표 없음·뻔한 내용·화면이 대본을 따라가지 않음·연출 과잉·말투 — 지난 기각(`manual/reviews.md`)은 대부분 렌더 전에 막을 수 있었습니다. 그래서 결정 지점(D1~D3)을 렌더 **앞**에 둡니다.

### 0-2. 규칙을 적는 법 (v38)
- 규칙은 **숫자 상한·하한이 아니라 이유와 목적**으로 적습니다 — 왜 하는가·어떤 상황에서·넘치면/모자라면 무엇이 무너지나·확인 질문 (`05` §0-0, README §5). 같은 원리라도 영상마다 알맞은 양이 다르기 때문입니다 (2026-11-17 사용자).
- 한 번의 반응을 금지·MUST 로 만들지 않습니다 — 층부터 정합니다 (README §3-1 규칙의 네 층, `rule_tiers.yaml`).
- `check` 의 **참고(ℹ️)** 는 측정값이고 실패가 아닙니다. 표시된 곳을 D3 화면 확인에서 사람이 봅니다.

> 사용자가 가리키는 대상(제목·썸네일·장면)이 애매하면 바꾸기 전에 확인합니다.

### 1-1. 모델 티어 — 메인은 Opus, Fable 은 중요할 때만 (2026-11-22 사용자: "그냥 opus로 세션진행하고 fable은 중요할때만 호출하게 해보세요 fable을 메인으로 하라고 해서 메인으로 햇더니 토큰이 녹았거든요")
> 처음 정한 것: "판단 … 부분은 fable이 복잡한 일은 opus 간단한 일은 sonnet입니다. 다른 프론티어 모델들도 이런식으로 티어가 나뉘는데 모델 이름과 버전만 다르다는 느낌으로" (2026-11-22). Fable 을 세션 메인으로 쓰니 긴 세션에서 토큰 소모가 감당되지 않아, **티어 구조는 두고 판단 티어 모델을 Opus 로** 바꿨습니다.

| 티어 | 모델 (지금, Anthropic) | 맡는 일 |
|---|---|---|
| **판단** (judge) | Claude **Opus 5.5** (메인 세션) | 무엇을 만들지·어느 쪽이 맞는지·통과인지 정하는 일, 일 나누기, D1~D4 정리·보고, 원고·대본 쓰기, 제목·썸네일 문구 |
| **복잡한 일** (complex) | Claude Opus 5.5 (`senior` 에이전트) | 대본 근거 검수표·구성요소 대조표(쓴 세션과 다른 새 맥락에서), 레퍼런스 분석, 장면표·연출 설계, 영상 검수 대조 |
| **간단한 일** (simple) | Claude Sonnet 5.5 (`worker` 에이전트) | 자료 수집·요약·목록·옮겨 적기·렌더·캡처·자막, 뉴스레터 수집 예약 작업 |
| **중요한 판단만** | Claude Fable 5.2 (`fable` 에이전트 — 비쌈) | ① 대본을 D2 에 내기 직전 최종 판단 한 번 ② 근거가 엇갈려 어느 쪽이 맞는지 정할 때 ③ 사용자가 "Fable 로"라고 할 때. 필요한 파일만 넘겨 짧게 묻고, 일상 작업에는 쓰지 않음 |

- **세션은 Opus 로 엽니다.** Fable 을 세션 모델로 쓰면 긴 대화 전체를 매번 비싼 모델이 다시 읽어 토큰이 크게 녹습니다. Fable 은 `fable` 에이전트로 작은 맥락에서만 부릅니다.
- **긴 작업은 새 세션에서:** 대화가 길수록 매 턴 다시 읽는 양이 커집니다. 매뉴얼·설정은 저장소에 있으니 새 세션도 같은 기준으로 일합니다. 예약 작업(정기 검토 등)도 매번 새 세션에서 돕니다.
- **설정 한 곳:** [`config/models.yaml`](../config/models.yaml) — 티어(judge·complex·simple)·단계 → 티어·제공사별 모델 이름. 여유가 생기면 판단 티어 한 줄만 다시 Fable 로 바꿉니다. 티어는 제공사 공통(Codex 칸은 비면 기본 모델).
- **새 모델이 나오면 다시 설정:** `models.yaml` 의 `providers`·`checked` 와 `.claude/agents/*.md` 의 model. 정기 검토가 30일마다 묻습니다.

### 2-1. 한 편씩 따로 진행 (v2)
- 세 편은 **각자의 S0~S9** 를 따로 갑니다. 다른 편의 결정을 기다리느라 멈추지 않습니다.
- 한 편이 결정 지점(★)에서 사용자를 기다리는 동안, 에이전트는 다른 편의 다음 단계를 진행합니다.
  ```
  AI     S0─S1 ★D1 ·········· S2─S4 ★D2 ······ S5─S6 ★D3 ··· S7─S8 ★D4 S9
  시사          S0─S1 ★D1 ···· S2─S4 ★D2 ······ S5─S6 ★D3 ··· S7─S8 ★D4 S9
  호기심               S0─S1 ★D1 ··· S2─S4 ★D2 ······ ...
  ```
- 결정 요청이 우연히 겹치면 한 메시지에 함께 보내되, 편마다 따로 답할 수 있게 나눕니다.

### 2-2. 결정 지점 — 보여 주는 것 · 묻는 것 · 기각되면 돌아갈 곳
| | 사용자에게 보여 주는 것 | 묻는 것 | 볼 시간 | 기각되면 |
|---|---|---|---|---|
| **D1 주제·형식** | `topic_card.md`: 후보 3개, 각각 질문 한 줄·`known` vs `new_angle`·점수·형식(ai)·핵심 자료 2개·뉴스레터 신호 | 어느 후보로? (다른 주제 지시 가능) | 3분 | S1b (이유를 카드 기준에 반영) |
| **D2 대본** | `script_v1.md` 전문 + 맨 위에 의도 한 줄·장 목록·**구성요소 대조표·13 §7 자체 검사 결과**(길이 대신, 2026-11-21 사용자) | 대본 절차·구성요소·이야기 흐름·깊이·말투 OK? | 10분 | S4 (구조 문제면 S3) |
| **D3 화면** | 샘플 영상 30~60초 + 장면표 요약(장면 type 분포) | 화면 방향 OK? | 3분 | S5 |
| **D4 최종 승인** | `final.mp4` + 제목 3 + 썸네일 A/B/C + `check` 결과 + 남은 일 | 통과 / 기각 + 이유 | 영상 길이 | 이유에 따라 S4·S5·S7 · 기각 사유는 `review --reject` → 매뉴얼 '반영 대기' |

- D1·D2 는 건너뛰지 않습니다. D3 는 사용자가 "샘플 없이 가자"고 하면 생략할 수 있습니다.
- 기각 때 사용자가 기준 영상(구판·다른 채널)을 지정하면 그 영상의 실제 설정·컷으로 화면 방향을 다시 잡아 D3 샘플로 확인합니다.
- 결정 요청에는 항상 **에이전트 추천 하나와 그 이유**를 붙입니다.

### 2-3. 작업 기록 — 수정하면서 작업하기
프로젝트 `REPORT.md` 에 단계마다 세 줄:
- **한 일**: 산출물 이름
- **혼자 판단한 것**: 매뉴얼에 기준이 없어 고른 것과 이유
- **막힌 것**: 접근 불가 자료·도구 오류·오래 걸린 곳

S9 에서 '혼자 판단한 것'을 §5 개정 기록에 옮기고, 사용자 OK 후에만 매뉴얼에 넣고 `manual-bump`.
작업 중 이 문서 자체가 실제와 맞지 않으면 그 자리에서 §5 에 적고 다음 결정 지점에 함께 묻습니다.

### 2-4. S3 첫 칸 — 목적 분간과 매체 질문 (2026-11-18 사용자, 근거 `docs/37`)
> "목적성 자체가 정보제공 목적이 큰지 아니면 취미나 유흥 즐길거리 목적인지 분간해야 해요. 그에 따라 연출이 달라지는 거구요" · "글과 PPT와 PDF 그리고 동영상의 특징과 차이점, 그리고 정보습득형·즐길거리형 등 시청자의 니즈를 생각해서 작업"

- **왜:** 같은 연출도 목적에 따라 득이 되기도 독이 되기도 한다. 정보 습득형에 이야기 연기를 길게 넣으면 핵심이 늦게 나오고, 즐길거리형에 요약판·숫자 쪽지를 넣으면 '설명 영상'이 되어 이탈한다.
- **어떻게 (S3, `02_script/intent.md` 맨 위):**
  ```
  목적: 정보 습득형 | 즐길거리형      (채널 기본: 시장·AI = 정보 습득형, 시사 = 반반이면 정보 습득형 쪽, 호기심 = 즐길거리형 — README §1-1)
  1) 시청자는 스스로 찾아왔나, 우연히 마주쳤나?
  2) 끝나고 남아야 할 것은 구조(이해)인가, 감정(여운)인가?
  3) 움직임을 이해에 쓸까, 몰입에 쓸까?
  ```
  세 답이 채널 기본과 다르면(예: 호기심인데 '구조'가 남아야 하는 편) 그 편만 바꾸고 이유를 한 줄 적는다.
- **연출 수단을 고르는 기준** (`docs/37` §2):
  - **정보 습득형** — 성공 기준 "이해했나": 말하는 숫자가 그 순간 생김·원인 → 결과 화살표·같은 축 비교·원문 형광펜, 근거(숫자·이름·출처)는 화면에 보임.
  - **즐길거리형** — 성공 기준 "다음이 궁금해 끝까지 봤나": 인물이 대본의 동사를 연기, 움직이는 소품으로 은유, 숫자 쪽지·정보 카드는 기억할 한 가지만.
- **매체 질문** (S5 장면 기획, `05` §0-0): 장면마다 "PPT 한 장이나 글 한 문단으로 바꿔도 똑같이 전달되는가?" — 그렇다면 무엇이 생기고·움직이고·바뀌어야 하는지 다시 본다.
- **검사:** `check` G4 SHOULD — `intent.md` 에 `목적:` 줄이 있는지만 본다 (어느 쪽을 골랐는지는 D2 에서 사람이 판단). 숫자 기준은 두지 않는다.

## 7. 연출 인계와 화면 검토

S5에서 [장면의 표현 방식](12-visual-storytelling.md)을 고른다. 행동이 중심인 컷은 시작 상태·주체·변화가 일어나는 발화·끝 상태를 적는다. 자료가 중심인 컷은 확인할 근거·출처·보여 줄 부분·읽는 시간을 장면표에 남긴다. 화풍·원화 승인과 동작이 담긴 영상 승인을 각각 기록한다. 같은 대본을 다른 에이전트가 이어받으면 기존 장면표를 먼저 재생한다. 연출을 바꾸려면 새 판본으로 제시한다.

글자를 가려도 행동이 읽혀야 한다. 상자·연결선·라벨의 움직임이 사건을 대신하면 다시 편집하고, 통계의 단위·분모와 출처 원문은 읽을 수 있게 둔다.

인계 자료는 `02_script/EDIT_CONTEXT.md`·장면표·사용 판본 (§6, [docs/42](../docs/42-script-to-motion.md)).

| 화면의 변화 | 등장·이동·선택·비교·확대·상태 변화 중 실제로 필요한 것 |

| 증거·한계 | 사실 주장이면 받치는 자료(팩트시트 번호), 재현이면 '재현' 표시 |

직전 같은 채널 편과 화면 구성이 많이 겹치면(QA 의 유사도 기록 등) 이 단계에서 이번 편이 무엇이 달라야 하는지를 장면표 맨 위에 적는다. 검수는 기술·서사·연출 QA 를 서로 다른 통과 조건으로 기록한다([06 EYE 6·7](06-checklist.md)).
