# 35. 매뉴얼은 한 번에 한 명만 — 담당자 1명 + 잠금 (2026-11-15)

> 사용자: "매뉴얼 작성을 이 에이전트 저 에이전트 중복해서 수정하지 않도록 깃 수정 등 파일관리는 한번에 한명만 하도록 하세요. 여기저기 뒤죽박죽 하지 말고 관리하자는 거예요. 병렬로 작업하는 경우가 분명히 생길 텐데 모두가 수정하면 관리가 엉망이 될 것 같아서요."
> 결정: **담당자 1명 + 잠금 (둘 다)** · 보호 범위 = **매뉴얼과 규칙 파일** · 이 체계를 main 에 합침.
> 계기: 같은 날 main 의 다른 세션과 이 세션이 각자 매뉴얼 v32 를 만들어 번호가 겹쳤음 (→ v34 로 다시 매김).

## 누가 무엇을
| | 매뉴얼 담당 (1명) | 다른 에이전트 (병렬로 몇 명이든) |
|---|---|---|
| 매뉴얼·규칙 파일 (`manual/OWNERS.yaml` 의 protected) | 잠금을 잡고 고침 → 버전 → main 반영 | **고치지 않음** — 제안함에 남김 |
| 사용자 검토·피드백 기록 | `review`·`feedback` (매뉴얼에 바로) | 같은 명령을 쳐도 **자동으로 제안함**으로 감 |
| 영상 프로젝트·렌더러·자료 | — | 각자 브랜치에서 자유롭게 (프로젝트 폴더는 만드는 세션 하나가 맡음) |
| SAVE 알림 자동 커밋 (`inbox/`) | — | 그대로 (보호 범위 밖) |

지금 담당: `manual/OWNERS.yaml` 의 `steward` (매일 밤 정기 검토 세션). 담당을 바꾸는 것은 사용자가 정한다.

## 잠금 (`python -m ytflow manual-lock …`)
- 잠금은 원격 브랜치 **`locks`** 의 `manual-lock.json` 한 파일. 그 파일만 바꾼 커밋을 push 해서 잡고 푼다 — 둘이 동시에 잡으면 늦은 쪽 push 가 거절되고, 쓰기 직전에도 원격 잠금을 다시 확인한다.
- `status` 누가 잡고 있나 · `acquire --purpose "…"` 잡기 (비었거나 내 것이거나 만료됐을 때) · `release` 풀기
- 유효 시간 26시간 — 담당은 매일 밤 정기 검토 때 다시 잡는다. 담당 세션이 멈추면 만료 뒤 다른 세션이 잡을 수 있다.
- 사용자가 다른 세션에 매뉴얼 작업을 맡기면: 그 세션이 `acquire --force --reason "사용자 허락: …"` (넘겨받은 기록이 잠금에 남음). 끝나면 `release`, 담당이 다음 밤에 다시 잡는다.
- `locks` 브랜치에 잠금 커밋을 올리는 것은 이 규칙에 따라 사용자가 허락함 (2026-11-15). 잠금 파일 말고는 아무것도 올리지 않는다.

## 막는 장치 (세 겹)
1. **명령**: `manual-bump` 은 잠금 없으면 멈춤. `review`·`feedback` 은 제안함으로. `manual-graph`·`manual-audit` 은 매뉴얼 파일을 다시 쓰지 않고 보기만. `manual-ui` 저장 버튼은 거절.
2. **Claude Code hook** (`.claude/settings.json` PreToolUse): 보호 파일을 Edit·Write 하려 하면 잠금을 확인하고, 없으면 이유와 함께 막음. 세션이 시작될 때 잠금 상태를 보여 주고 git hook 을 켬.
3. **git pre-commit** (`.githooks/pre-commit`, `git config core.hooksPath .githooks`): 보호 파일이 든 커밋을 잠금 없이 하면 거절. Codex 등 다른 에이전트도 이 hook 과 AGENTS.md 규칙을 따른다.
급히 혼자 쓸 때만 `YTFLOW_MANUAL_GUARD=off` (사용자가 직접 할 때).

## 제안함 (`proposals/manual/`)
- `python -m ytflow manual-propose "내용" [--kind feedback|review|fix|rule|tool] [--project …]` → `proposals/manual/<시각>-<브랜치>.md` 파일 하나 = 제안 하나 (이름이 안 겹쳐 병렬로 써도 충돌 없음).
- 담당의 정기 검토(`manual-audit`)가 '제안함' 항목으로 보여 주고, 담당이 반영(feedback·review·매뉴얼 수정)한 뒤 제안 파일의 `status: done` 으로 바꾼다.

## main 에 반영
담당이 매뉴얼을 고치면 담당 브랜치에서 PR 을 만들어 main 에 합친다 (사용자 허락 2026-11-15: 매뉴얼 담당은 자기 매뉴얼 PR 을 합칠 수 있음). 다른 세션의 PR 이 보호 파일을 건드리면 합치기 전에 담당에게 넘긴다(제안함).

## 보호 범위 바꾸기
`manual/OWNERS.yaml` 의 `protected`·`open`. 저장소 전체를 한 명만 고치게 하려면 `protected` 에 `"**"` — 단, 매일 아침 시장 브리핑·30분마다 오는 SAVE 알림 커밋도 담당을 기다리게 되어 병목이 생긴다 (2026-11-15 사용자에게 설명함).
